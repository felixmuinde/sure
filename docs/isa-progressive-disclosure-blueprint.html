Progressive Student Data Disclosure
Blueprint

A phased plan for revealing ISA data to students based on their contract stage — designed to grow alongside multi-country expansion and future ISA product types.

Kenya ISA Statuses — Confirmed Raw Values

Active journey — normal progression
Stage 1
Application
"Application"
Student has submitted an ISA application. No commitment or contract yet. ISA terms not finalised.
✅ Status badge ✅ "Under review" copy 🔒 All financial data
Stage 2
ISA Contract Signed
"ISA Contract Signed"
Contract terms agreed and signed. Education is starting. Chancen has not yet disbursed funds to institution.
✅ Status badge ✅ Max approved amount ✅ Total instalments ⚠ Repayment % (API gap) 🔒 Financing progress 🔒 All repayment data
Stage 3
Pre-graduation Meeting Attended
"Pre-graduation meeting attended"
Student is near end of studies. Chancen has been paying tuition invoices. Pre-grad milestone reached.
✅ All Stage 2 data ✅ Amount financed to date ✅ Financing progress bar 🔒 Repayment data (not yet)
Stage 4
Graduated
"Graduated"
Student has completed their education. Repayments begin once income exceeds the threshold.
✅ All Stage 3 data ✅ Repayment countdown (if started) ⚠ Next payment due (API gap)
⚠ Confirm repayment trigger
Stage 5
Repaying
"repaying" (Flutter enum)
Income above threshold — student is making monthly ISA repayments. May not be a separate Metabase status; confirm with data team.
✅ All Stage 4 data ✅ Total repaid ✅ Instalments paid / outstanding ✅ Repayment progress ring
⚠ Warehouse status TBC
Exit states — off the main path
Exit A
Application Cancelled
"Application Cancelled"
Student cancelled their own application before signing. No financial commitment made.
✅ "Cancelled" status badge ✅ Re-apply CTA (future) 🔒 All financial data
Exit B
Contract Revoked
"Contract revoked"
Chancen terminated the ISA contract, typically due to eligibility or compliance reasons. Student may have obligations outstanding.
✅ Warning status badge ✅ Amount financed (if any) ✅ Contact support CTA
Exit C
Drop Out
"Drop out"
Student left their education programme before completion. ISA obligations may still apply depending on contract terms.
✅ Status badge ✅ Amount financed to date ✅ Contact support CTA
Exit D
Drop Off
"Drop off"
Student stopped engaging with Chancen during repayment or education. Similar to Drop Out but may indicate lost contact rather than active withdrawal.
✅ Status badge ✅ Outstanding balance (if any) ✅ Contact support CTA
⚠ Confirm vs Drop Out
Ambiguity to resolve with the team:
  • Drop Out vs Drop Off — are these truly distinct statuses or legacy naming? Confirm whether both should show the same UI or if one implies ongoing obligations.
  • Graduated vs Repaying — does "Graduated" automatically transition to repayment, or is there a separate trigger? The Flutter enum has repaying but no matching Kenya raw status — confirm if "Graduated" is the repayment state in the warehouse.
  • Flutter enum extras — paused, service_fee_mode, completed appear in the Flutter enum but not in the Kenya raw list. Are these used in other countries, or are they planned states?
Status Standardization Map
Kenya uses human-readable strings with spaces and mixed case. Other countries will likely use different strings. Before expanding, agree on a canonical code that all countries map to — the app's disclosure logic should work off the canonical code, not raw strings.
Proposed approach: Keep raw strings in the warehouse (each country manages their own). The Rails provider normalizes to a canonical isa_status_code before returning it in the API. The Flutter app uses the code exclusively. Raw strings are only visible in admin/debug views.

ISA Type Considerations
No isa_type field exists today. Different ISA products will need different disclosure rules and UI copy.
Current state: A single ISA product is assumed. As Chancen expands products and countries, disclosure rules will need to branch by ISA type. The status pipeline above may also differ per product — for example, a bootcamp ISA may not have a "Pre-graduation meeting attended" stage.

Standard ISA — Kenya (current baseline)

  • Repayment % of net income (e.g. 15%)
  • Fixed instalment count (e.g. 48 months)
  • Max financing cap (e.g. KES 268,240)
  • Income threshold before repayments trigger
  • All current stage pipeline and UI cards apply

Short-Course / Bootcamp ISA (hypothetical)

  • Shorter repayment period (e.g. 24 months)
  • No "Pre-graduation meeting" stage
  • Different income threshold
  • Lower max financing amount
  • May replace "Instalments" card with lump-sum view

Partner Org / Employer-Linked ISA (hypothetical)

  • Employer-linked — repayments may be payroll deducted
  • Different copy: "Your employer is contributing…"
  • Employer contribution split view
  • Employer contact card may appear

Cross-Border ISA (future)

  • Student studied in one country, repaying from another
  • Currency conversion display needed
  • Two Metabase question IDs may be needed
  • Jurisdiction for repayment threshold may differ
Design decision needed: Add isa_type to StudentAccountData (Ruby struct), StudentAccount (Flutter model), and the API JSON response. Confirm with the data team whether this column exists in the Metabase warehouse. Once available, the Flutter _visibilityFor() helper receives both status and isaType to drive card visibility.

POST /api/v1/family_assignment already routes students into country-specific families. Each country will likely have different raw status strings and different ISA terms.

Single-point bottleneck: Setting.metabase_student_question_id is a single global value. When RW/ZA/GH go live, this must become per-country — e.g. a JSONB hash { "ke": "42", "rw": "57" } or separate fields like metabase_student_question_id_ke. MyAccountController would select by current_resource_owner.family.country.
Currency display: The currency field is already returned by the API (defaults to KES). Flutter should use this field for all monetary formatting — never hardcode KES.
Family Creation & Student Categories
No "student" concept exists in the data model today. Here's what exists and what needs to be designed.
Current State

User → Family (by country)

  • User.role: guest / member / admin / super_admin — no "student" role
  • Family.country: ISO code for routing (KE / RW / ZA / GH)
  • Family.moniker: "Family" or "Group" — no ISA concept
  • Students identified purely by email lookup in Metabase
  • No cohort, program, intake year, or institution fields
Future Design (propose to team)

Student Profile Layer

  • Family.family_type enum: personal | student_isa | partner_org
  • User.student_profile or a StudentProfile join model
  • Student categories: cohort, program, intake year, institution
  • ISA type tag on family or user level → drives disclosure rules
  • Account.metadata JSONB (already exists — PR #27) as bridge before formal model
Gap: Student Categories

What Categories Students Can Belong To

None currently exist in code. Likely categories to design:

  • By program: Engineering, Business, Health, etc.
  • By institution: University / bootcamp name
  • By intake: Jan 2024, Sep 2024, etc.
  • By ISA type: Standard / Short-course / Employer-linked
  • By country: Already handled via Family.country
Where Logic Should Live

Disclosure Rule Architecture

  • Flutter: _visibilityFor(IsaStatus, {IsaType?, String? country}) → Set<String> of visible section keys
  • Rails: MyAccountController selects Metabase question by family.country + optional isa_type
  • Admin: each country × ISA type combo gets its own Metabase question ID in Settings
  • status_code drives gating; isa_type drives which cards and copy appear
Bridge option (before full student profile model): Use Account.metadata (PR #27, already merged) to store ISA metadata per account — e.g. { "isa_type": "standard", "cohort": "jan_2024", "institution": "Strathmore" }. Avoids a new migration; can be promoted to a proper model later. Readable from GET /api/v1/accounts/:id.
